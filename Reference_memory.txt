Named targets (defined in workflow/Snakefile — see section 2):
  all          — default target if none given: preprocess + build, every
                 discovered basin (rules 01-16)
  preprocess   — rules 01-12 only (everything up to and including the
                 upstream-boundary check), every discovered basin
  build        — rules 13-16 only (SFINCS build, spin-up, sanity checks,
                 main event run) — assumes preprocess outputs already exist

Key flags:
  --cores N          Required. Max parallel jobs. N=1 is fine for a single
                      basin (the DAG is a long linear chain per basin
                      anyway); use a higher N when running multiple basins
                      so independent basins' jobs can run concurrently.
  -n, --dry-run       Preview the DAG (which jobs, in what order, and WHY
                      each is scheduled) without executing anything. Always
                      dry-run after editing rules/config before a real run.
  --forceall          Force every scheduled job to re-execute even if its
                      outputs already exist and look up to date. Combine
                      with a restricted target (see target_basins below) to
                      force-rerun just one basin without touching others.
  --forcerun RULE     Force only a specific named rule (and everything
                      downstream of it) to rerun, leaving unrelated
                      up-to-date outputs alone — narrower than --forceall.
  --until RULE        Run the DAG only up to and including RULE, then stop
                      (e.g. --until build_sfincs to assemble the SFINCS
                      input files without actually executing the solver).
  --config KEY=VALUE  Override/extend a config.yml value from the CLI for
                      this run only (parsed as YAML, so lists/numbers work:
                      --config target_basins="[2433835]"). Does not modify
                      config.yml on disk. See "RUNNING A SINGLE BASIN" in
                      section 14 for the basin-restriction use of this.
  --rerun-triggers mtime
                      By default Snakemake also reruns a job when its CODE
                      or PARAMS changed since the last run (provenance
                      tracking), even if the output file's mtime looks
                      current — this is usually what you want, but if a
                      formatting-only script edit is triggering unwanted
                      reruns, this flag switches to mtime-only triggering.
                      (Alternative for one specific output file: snakemake
                      --cleanup-metadata <outfile> wipes its provenance
                      record without touching the file itself.)
  --keep-going        Continue running other, independent jobs if one job
                      fails, instead of stopping the whole run immediately —
                      useful when running several basins at once and one
                      basin's data has a problem.
  --unlock            Release a stale ".snakemake/locks" lock left behind
                      by a crashed/killed run before you can run again.
  -p, --printshellcmds
                      Print the actual shell command each job runs (mainly
                      useful for the SFINCS solver invocations in rules 14/16).
  --rulegraph / --dag
                      Print the DAG in Graphviz dot format (pipe to `dot -Tpng`
                      to render) — needs graphviz installed.

Everyday examples:
  Dry-run everything:
    snakemake -n --cores 1
  Dry-run just the build stage:
    snakemake -n build --cores 1
  Force a full real rerun of ONE basin only (see section 14 for how
  target_basins works and how BASINS is normally discovered):
    snakemake build --cores 1 --config target_basins="[2433835]" --forceall
  Rerun only from build_sfincs onward (e.g. after a config.yml change to
  `sfincs`) without redoing preprocessing:
    snakemake build --cores 1 --forcerun build_sfincs
  Run specific flood scenarios:
    snakemake build --cores 1 --config target_basins="[2433835]" target_scenarios="['coast_100']"

DAG shape, not a strictly linear chain:
  - Rules 05a/05b/05c (inside 05_static_terrain_data.smk) are a genuinely
    linear sub-chain — elevation → landuse/zsini/sea_mask → roughness, each
    reprojecting onto the previous step's exact grid.
  - Rule 09 (condition_elevation, rule name enforce_river_monotonicity) only
    needs rule 08's cleaned network topology/width (reach_id, rch_id_dn,
    is_seed, width) — never rivdph — so it runs BEFORE either depth-
    estimation rule below, not after or in parallel with them. It modifies
    the ELEVATION RASTER (not the network), producing
    elevation_conditioned.tif (native FathomDEM resolution) AND a second
    copy resampled onto rule 08c's shared SFINCS grid
    (elevation_conditioned_sfincs_grid.tif) — that second copy exists so
    rule 10-modelled's calibration and rule 13's production build both use
    the identical coarse background elevation instead of each independently
    (and potentially inconsistently) resampling from the native file.
    ALWAYS runs — no longer opt-in.
  - Rule 10 is a pair of SIBLING ALTERNATIVES — depth_estimation_empirical
    and depth_estimation_modelled — selected by
    river_processing.depth_method ("empirical" | "modelled"), NOT a
    sequential chain and NOT both run. Exactly one is ever DEFINED (each
    .smk file guards its rule behind a module-level `if`, not a runtime
    skip) because both would otherwise declare the same output files
    (river_network_depth_estimated.gpkg, river_burned_dem.tif,
    river_burned_dem_sfincs_grid.tif) and Snakemake would raise
    AmbiguousRuleException. Every downstream consumer (rule 11, rule 13)
    reads those unified filenames with no depth_method-conditional logic of
    its own — it doesn't know or care which sibling actually ran.
      - empirical (depth_estimation_empirical) — formula-driven, no
        simulation: Leopold-Maddock power-law hydraulic depth, optionally
        blended with the Nienhuis/O'Brien estuarine depth model near the
        coast (river_processing.empirical_estimation.estuarine_depth).
        Burns its own channel directly into a native-resolution DEM (there
        is no separate preburn/burn-DEM rule anymore — see section 5).
      - modelled (depth_estimation_modelled) — SFINCS-based calibration:
        iteratively builds and re-runs a disposable, confined calibration
        model to derive a per-cell riverbank weir crest + channel
        excavation depth from the model's OWN simulated water surface,
        correcting for backwater/junction coupling a purely local
        power-law estimate can't see. Also produces the coastal_protection_
        weir.gpkg that rule 13 imports directly (rule 13 never re-derives
        its own weir when this sibling ran). See section 5 for the full
        calibration design (rounds, convergence, probes).
    Rule 09 (enforce_river_monotonicity) is a dependency of BOTH siblings
    (each needs the conditioned elevation as its un-excavated calibration/
    power-law bed) but is otherwise unrelated to which sibling is active.
  - Rule 11 (11_testing.smk) contains TWO diagnostic-only, mutually
    independent rules, neither gating build_sfincs (13):
    test_upstream_boundary (needs rule 07's outputs + whichever rule-10
    sibling ran) and test_bifurcation_calibration_options (needs rule 07's
    river_forcing.nc + the raw SWORD catalogue sources directly). Nothing
    downstream depends on either's output.
  - Rule 08b (optimize_grid_resolution) computes a per-basin SFINCS grid
    resolution from channel width (20th-percentile width among
    discharge-thresholded reaches) plus a cell-count budget, replacing a
    single fixed sfincs.grid.resolution for every basin. Needs rule 08's
    own bankfull_discharge_acc column, so it cannot run any earlier. Rule
    08c (build_sfincs_grid) then builds the SFINCS regular grid ONCE from
    that resolution and persists its transform/shape/CRS so rule 09
    (elevation resampling), rule 10-modelled (calibration), and rule 13
    (production build) all target the byte-identical grid instead of three
    independent HydroMT resamples that could silently drift apart by a
    pixel. Rule 07 cannot reuse 08b's output for its own diagnostic-only
    resolution annotation (07 → 08b → 08 → 07 would be a cycle, since 08b
    needs 08's column and 08 needs 07's crossing points) — 07 uses the
    static sfincs.grid.optimize_resolution.default_resolution_m instead.
  - Rule 07 (get_boundary_forcings) sits between the raw network (06) and
    the cleaned network (08) because rule 08 genuinely needs rule 07's
    output (the boundary crossing points) to seed its BFS cleaning — rule
    07 also builds surge_forcing.nc, unrelated to the river network, so it
    cannot be collapsed into a 06-family sub-letter.

RULE SUMMARY (in DAG order):
  00  common.smk     — catalogue helper (CATALOGUE / catalogue_path), wildcard
                        constraints, BASINS list. BASINS is auto-discovered from
                        delta_polygons but can be restricted via an optional
                        CLI-only config override, target_basins (not a
                        config.yml key) — see "RUNNING A SINGLE BASIN" in
                        section 14.
                        Also the scenario axis: loads scenarios_file
                        (config/scenarios.yml), validates each scenario's
                        surge_rp (COAST-RP tabulated values only) and
                        river_rp (2–1000 yr), defines scenario_params(name)
                        (-> {mode, surge_rp, river_rp}, mode DERIVED via
                        derive_forcing_mode from which RP is set — see
                        section 4/9) and the {scenario} wildcard constraint.
                        "default" is a REAL, REQUIRED entry in scenarios.yml
                        (00_common.smk raises ValueError if missing) used
                        whenever target_scenarios isn't given; SCENARIOS
                        comes from the CLI-only target_scenarios override,
                        else ["default"].
  01  separate_deltas — clip delta polygon per basin_id (BasinID2)
  02  modeldomain    — domain bbox, UTM CRS, domain.gpkg. Domain is ALWAYS
                        the delta polygon itself (reprojected to
                        auto-detected UTM) — the old "basins" mode (bbox
                        around intersecting HydroBASINS) was removed
                        entirely. {basin_id}_intersecting_basins.gpkg is
                        still written (schema compatibility) but is now just
                        a copy of the domain polygon, n_intersecting_basins
                        hardcoded to 0.
  03  get_land_polygons — clip OSM land polygons to domain. Runs right after
                        domain (02) because it's a PREREQUISITE of elevation
                        (05a), landuse (05b), and river network (06). Also
                        used by build_sfincs (13) to define waterlevel
                        boundary cells: active-domain edge cells NOT covered
                        by land polygons become mask=2 (waterlevel boundary).
  04  get_protection_levels — FLOPROS × WRI geounit dominant protection
                        standard per delta polygon, split by riverine/coastal
                        hazard. Depends ONLY on the delta polygon (01) —
                        unrelated to elevation/landuse/terrain. Always runs
                        (no `enabled` toggle — see section 4's flopros_range
                        entry); rule 07's use of its output is asymmetric,
                        not a single shared toggle (see section 7).
  05a get_elevation    — elevation_merged.tif (FathomDEM + GEBCO merge, see
                        section 4). Genuinely sequential with 05b/05c.
  05b get_landuse      — landuse.tif + sea_mask.tif; also builds the full
                        zsini.tif (needs 05a's elevation_merged.tif + land
                        polygons).
  05c get_roughness    — roughness.tif (needs 05b's landuse.tif).
  06  get_river_network — river_network.gpkg; clips SWORD to the domain and
                        writes it straight out. Needs land polygons (03) +
                        landuse (05b, for the plot's water-body overlay only)
                        — does NOT read elevation (05a) or perform any
                        elevation sampling/monotonicity enforcement anymore
                        (that logic, and the max_elevation attribute it used
                        to produce, were removed — see section 6).
  07  get_boundary_forcings — surge (CoastRP EVA) + river (GloFAS EVA)
                        forcing NetCDFs, GRDC bias correction, protection-
                        level netting (uses 04's output). Needs 06's raw
                        (uncleaned) river network — this rule's output
                        (crossing points) is what rule 08 cleans FROM.
  08  clean_river_network — BFS from boundary crossings (07's output) →
                        river_network_clean.gpkg + delta_outflow_points.gpkg
                        (outline-crossing points fed to rule 13 as SFINCS
                        outflow boundary, mask=3); width normalization.
  08b optimize_grid_resolution — per-basin SFINCS grid resolution; needs 08's
                        own bankfull_discharge_acc column. See DAG-shape
                        note above.
  08c build_sfincs_grid — builds the SFINCS regular grid ONCE from 08b's
                        resolution and persists transform/shape/CRS so rule
                        09, rule 10-modelled, and rule 13 all target the
                        identical grid. See DAG-shape note above.
  09  condition_elevation (rule name enforce_river_monotonicity) — ALWAYS
                        runs (no longer opt-in). Enforces monotonic
                        non-increasing DEM elevation along every river
                        centerline (downstream direction) →
                        elevation_conditioned.tif (native resolution) +
                        elevation_conditioned_sfincs_grid.tif (resampled
                        onto 08c's shared grid) + river_elevation_max.json
                        (max conditioned centerline elevation, feeds the
                        active-cell mask's elevation ceiling in rule
                        10-modelled/13). Needs only rule 08's topology/
                        width, not either rule-10 sibling's output — see
                        DAG-shape note above.
  10  depth_estimation_empirical / depth_estimation_modelled — SIBLING
                        ALTERNATIVES selected by
                        river_processing.depth_method; see the DAG-shape
                        note above for the full design (why they can't both
                        be defined, what each does). Both write
                        river_network_depth_estimated.gpkg,
                        river_burned_dem.tif, and
                        river_burned_dem_sfincs_grid.tif; modelled also
                        writes coastal_protection_weir.gpkg.
  11  testing         — TWO diagnostic-only side-branch rules (11_testing.smk),
                        neither gates build_sfincs (13):
                          test_upstream_boundary — wave-propagation check
                            (needs 07 + whichever rule-10 sibling ran — see
                            section 8).
                          test_bifurcation_calibration_options — compares
                            discharge partitioning at every bifurcation
                            between the original and manually-corrected
                            SWORD sources (needs 07's river_forcing.nc +
                            the raw SWORD catalogue entries directly, not
                            rule 06's output — see section 8).
  13  build_sfincs_skeleton (basin-level, 2026-08-04 split) + build_sfincs
                        (per-scenario forcing only, since the same split) —
                        HydroMT-SFINCS model build (regular grid only);
                        elevation source priority (in the
                        skeleton): river_burned_dem(_sfincs_grid) (10) >
                        elevation_conditioned(_sfincs_grid) (09) -- a
                        TWO-level fallback, NOT three: the raw
                        elevation_merged.tif (05a) is never used here at
                        all, only elevation_conditioned (native and
                        SFINCS-grid resolution). The skeleton's own input
                        key/variable/catalog key were literally named
                        "elevation_merged"/"local_elevation_merged" until
                        2026-08-04 despite always pointing at
                        elevation_conditioned.tif -- a stale name from
                        before rule enforce_river_monotonicity existed,
                        fixed for clarity (no behavior change). build_sfincs
                        (forcing-only) does NOT execute the SFINCS solver
                        either (that happens in rule run_spinup/run_event).
                        Scenario-aware: build_sfincs's own outputs live
                        under runs/{scenario}/; forcing_mode /
                        design_rp_river_yr / design_rp_surge_yr are all
                        derived per-scenario via scenario_params(wildcards.
                        scenario) — there is no config-level mode setting
                        anymore (see section 4/9).
  14  run_spinup      — runs a short SFINCS spin-up simulation (the solver's
                        FIRST execution in the pipeline) to produce a
                        restart file (grid-type agnostic).
  15  sanity_checks   — post-run inundation ratio checks + flood animation
                        (grid-type agnostic; SPIN-UP output only — velocity
                        animation was removed entirely, see section 14).
  16  run_event       — runs the MAIN flood-event simulation: the sfincs.inp
                        rule 13 already wrote (tstart = spin-up end,
                        tstop = end of the full forcing timeseries,
                        rstfile = rule 14's restart file) executed directly
                        in sfincs_root (not a subdirectory). Produces the
                        event's own sanity-check-style diagnostics
                        (inundation-ratio map, flood animation) plus a
                        per-timestep flooded-area/flood-volume CSV.
  17  flood_metrics   — calculated flood metrics per scenario from rule
                        16's finished event run; cheap postprocessing only,
                        never re-runs SFINCS. Writes
                        runs/{scenario}/metrics/max_flood_depth.tif
                        (downscaled max-depth GeoTIFF — input for later
                        flood-source attribution / adaptation measures) and
                        flood_metrics.csv (one row of scalar risk metrics
                        via postprocessing.compute_risk_metrics; column
                        names match legacy analyse.py risk_metrics.csv).
                        Config: metrics.hmin, metrics.urban_landuse_code
                        (TOP-LEVEL config keys, not nested under sfincs).

NOTE: rules 13, 14, 15, 16, 17 (and their visuals) are scenario-aware — all

5. TERRAIN & DATUM CORRECTION (rule 05a) + ELEVATION CONDITIONING (rule 09)
   + RIVER-BED BURNING (rule 10, both siblings)

FathomDEM is the only coastal DEM source, with no elevation clipping (it is
not restricted to low-lying coastal areas). Vertical datum correction is
mandatory, not optional.

Pipeline in 05a_get_elevation.py:
  1.  Merge FathomDEM tiles for the domain → topo_utm (UTM, coverage-weighted
      "nan-aware" resampling; /100 for the raw centimeter storage).
  1b. Clip topo_utm to NaN wherever the DeltaDTM validity mask (catalogue
      entry deltadtm_mask) marks a pixel as ocean — src.raster.
      clip_ocean_from_topo, only mask value 1 counts as ocean (see the
      catalogue entry's comment for the full, empirically-verified 4-class
      breakdown; do NOT trust a pasted description from elsewhere without
      re-verifying against this repo's actual raster). FathomDEM is
      terrestrial and reports spurious near-zero/shallow "elevation" over
      open water — this clip lets step 4's merge fall back to GEBCO there.
  2.  Vertical datum correction, EGM2008 → GOCO06s (MANDATORY): add the geoid
      offset N_EGM2008 − N_GOCO06s (pyshtools synthesis) to every valid
      FathomDEM pixel. No MDT subtraction is applied to the DEM itself — only
      the geoid offset.
  3.  Clip GEBCO to the domain, resample to the working UTM grid, and
      re-reference it to GOCO06s by subtracting the MDT (HYBRID-CNES-CLS2022)
      — extrapolated over land via inverse-distance weighting before
      resampling (needed so the subtraction doesn't NaN-poison nearshore
      GEBCO pixels whose receptive field straddles a land-side nodata cell).
      Applied to EVERY valid GEBCO pixel (not just at sea), since GEBCO may
      also fill land-side gaps in step 4.
  3b. Clamp gebco_utm to a floor of -terrain.gebco_max_depth_m (default
      7.0 m) — SFINCS's CFL-driven internal time step is set by the whole
      domain's single deepest active cell, and it gets its offshore forcing
      prescribed at the boundary rather than resolving open-ocean dynamics
      itself, so genuinely deep water only costs runtime for no modelling
      benefit. This interacts directly with step 1b above: the DeltaDTM clip
      lets MORE of GEBCO's real (deeper) bathymetry through than before (it
      used to be masked by FathomDEM's bogus near-zero values), which is
      what made this clamp necessary in the first place — confirmed live,
      basin 2433835's merged minimum went from -27.79 m (1b alone, no clamp)
      to exactly -7.00 m (1b + 3b, default depth).
  4.  HARD MERGE (no land-polygon mask, no gradient blend): merged =
      FathomDEM wherever it has valid data, GEBCO everywhere else. Purely
      driven by FathomDEM's own nodata pattern, not an independent land/sea
      classification. A defensive fillnodata covers the rare case where
      neither source has data for a domain pixel.
  5.  Write elevation_merged.tif (the only raster 05a writes).
  6.  Diagnostic plots (all always produced — datum correction is
      mandatory): 05a_elevation.png (main elevation map),
      05a_elevation_geoid_offset.png, 05a_elevation_mdt_ocean.png,
      05a_elevation_datum_correction.png (DEM correction delta),
      05a_elevation_gebco_correction.png (GEBCO correction delta).

zsini.tif is built in rule get_landuse (05b), not 05a — 05b already needs
land_polygons + elevation_merged for its own reprojection step, and zsini
genuinely needs the land/water-body split. 05b_get_landuse.py: reprojects
landuse onto elevation_merged.tif's grid, then rasterizes land_polygons onto
that same grid to get the initial land/sea split (0.0 m at sea, nodata on
land), overrides landuse==200 (water body) cells to 0.0, and excludes any
cell with no elevation data. Plots: 05b_landuse.png, 05b_zsini.png.

ELEVATION CONDITIONING (rule 09, rule name enforce_river_monotonicity —
ALWAYS runs, no longer opt-in):
  This rule modifies the DEM (not the river network) — it conditions the
  ELEVATION RASTER, using the river network purely as a guide for where and
  in what order to walk. enforce_river_monotonicity() in
  src/river_conditioning.py: topological (Kahn's algorithm) walk over the
  CLEANED river network (river_network_clean.gpkg, rule 08's output — only
  topology/width, reach_id/rch_id_dn/is_seed/width, are needed; rivdph does
  not exist yet at this point in the DAG, since this rule runs BEFORE both
  depth-estimation siblings), enforcing a per-reach running-minimum along
  centerline pixels so DEM elevation never increases downstream.
  Bifurcations inherit the min of all upstream parents; headwaters seed from
  their own first valid pixel.
  Outputs: elevation_conditioned.tif (native FathomDEM resolution) AND
  elevation_conditioned_sfincs_grid.tif (the same conditioned surface
  resampled onto the shared SFINCS grid rule 08c built) — this second copy
  exists so rule 10-modelled's calibration model and rule 13's production
  build both use the IDENTICAL coarse background elevation instead of each
  independently letting HydroMT resample from the native file. Also writes
  river_elevation_max.json (max conditioned centerline elevation, always
  attained at a seed reach) — consumed by sfincs.grid.active_mask (rules
  10-modelled/13) to set the active-cell elevation ceiling.
  Uses the shared _sample_line_cells() helper, defined in
  src/river_network.py.
  Diagnostic plot: 09_condition_elevation.png (n_seeds × 2 grid of
  before/after downstream elevation profiles per seed reach).

RIVER-BED BURNING (now folded into rule 10 — both empirical_depth_estimation
and modelled_depth_estimation burn their own channel directly; there is no
longer a separate preburn rule or burn-DEM rule):
  Historically this was two more rules downstream of conditioning
  (river_preburn → burn_river_dem). That chain was consolidated: each rule-10
  sibling now calls compute_river_bed_points() (src/river_preburn.py — same
  function, still samples a point at every DEM-pixel step along each
  centerline via the shared _sample_line_cells(), rivbed = DEM − rivdph)
  immediately followed by burn_river_channel() (src/river_burn.py) IN THE
  SAME SCRIPT, rather than persisting an intermediate zbed_anchors.gpkg file
  for a later rule to consume — there is no zbed_anchors.gpkg output anymore
  (check each rule-10 .smk's `output:` block if in doubt).
  burn_river_channel() burns each reach independently, using ONLY that
  reach's own bed-point anchors and its own full centerline (no cross-reach/
  cross-tile contamination possible by construction — this was originally
  written to avoid a confirmed hydromt_sfincs cross-tile-contamination bug
  in its own burn_river_rect, which matched each subgrid tile's local river
  line against the GLOBAL, un-clipped anchor set with no distance cutoff).
  At each reach-to-reach junction, a synthetic boundary anchor
  (_junction_value()) is inserted valued as the AVERAGE of the immediate
  upstream/downstream neighbour(s)' own nearest anchor, removing what would
  otherwise be a flat-clamp discontinuity where two reaches meet.
  Extrapolation beyond a reach's own anchor range is CLAMPED (not linear),
  to avoid overshoot.
  Each rule-10 sibling writes BOTH a native-FathomDEM-resolution burn
  (river_burned_dem.tif) and a SFINCS-grid-resolution burn
  (river_burned_dem_sfincs_grid.tif, via the same burn_river_channel call
  against rule 08c's shared grid) — rule 13 registers the native one as a
  HIGHER-PRIORITY elevation_list entry ahead of elevation_conditioned/
  elevation_merged (first-source-wins merge; gaps still fall back to the
  existing DEM for everywhere else: ocean, floodplain), and never re-derives
  its own burn or calls hydromt's own burn_river_rect.
  The MODELLED sibling's burn is not a one-shot calculation like the
  empirical sibling's: it is the end product of an iterative SFINCS-based
  calibration (river_processing.river_depth_modelling in config.yml — see
  section 4) that builds and re-runs a disposable, confined calibration
  model across a "round 0" isolated-confinement pass plus up to
  n_correction_iterations further correction rounds, using the model's OWN
  simulated water surface each round to raise the riverbank weir crest
  wherever it's overtopped (with a minimum-step floor so the correction
  can't stall on a vanishingly small residual), converging once the crest
  contains the flow everywhere AND the realized flooded-cell count has
  stabilized, then spending one further round tightening the crest down to
  a fixed freeboard margin above the converged water level (reverting that
  last tightening, round-by-round-verified, if it turns out not to hold).
  This produces BOTH the final rivdph/river_burned_dem AND
  coastal_protection_weir.gpkg (rule 13 imports the weir directly rather
  than re-deriving one). Treat this summary as an orientation map only —
  the actual round-by-round mechanics (including the coastal- and
  river-boundary-land probe mechanisms used to verify containment beyond
  the centerline) live in 10_depth_estimation_modelled.py itself and are
  too detailed to keep faithfully mirrored in this document long-term.

HYDRAULIC + ESTUARINE DEPTH (rule 10-empirical, depth_estimation_empirical,
ONLY — see rule 10's DAG-shape note in section 2; the "modelled" sibling
does not run any of this, it derives depth from its own SFINCS calibration
instead):
  - Hydraulic depth from Leopold-Maddock: depth = c × Q^f, applied DIRECTLY
    to bankfull_discharge_acc (river_processing.empirical_estimation.
    hydraulic_geometry.{c, f}) — src.river_network.compute_hydraulic_depth.
    Deliberately NOT derived by dividing a width-relation's implied
    cross-sectional area by the real SWORD width (would silently undersize
    every burnt channel by 1-2 orders of magnitude at this pipeline's
    basin-accumulated discharge scale — see the function's own docstring).
    A TODO in the function notes the same formula is applied regardless of
    coastal proximity, which may overestimate depth in tidally-influenced
    reaches vs. the true inland-river regime.
  - Estuarine blend (river_processing.empirical_estimation.estuarine_depth,
    gated by its own `enabled` — independent of depth_method): if enabled
    AND a Nienhuis delta match is found within max_match_dist_km, loads the
    Nienhuis 72-delta table (load_nienhuis), matches basin→delta by spatial
    proximity (match_basin_to_delta), then compute_estuarine_depths() —
    O'Brien (1969) mouth cross-sectional area A0 = C·P^alpha, convergence
    length L_A = L_e / convergence_ratio_k, depth d(x) = A0·exp(-x/L_A) /
    W_total_mouth (normalised by summed mouth-reach width, end_reach==2),
    linear blend zone (±blend_fraction of L_e) around the estuarine/fluvial
    boundary with the power-law rivdph, floored at min_depth_m. New
    columns: rivdph_estuarine, rivdph_powerlaw, rivdph_blend_alpha. If
    disabled or no match found: passthrough (power-law rivdph unchanged).
  - enforce_mouth_depth_monotonic() (src/estuarine_depth.py) — applied
    UNCONDITIONALLY regardless of estuarine_depth.enabled: floors a mouth's
    final depth at max(own power-law estimate, upstream neighbour's depth),
    mirroring enforce_mouth_width_monotonic (rule 08) for depth.
  - Then burns its own channel directly (compute_river_bed_points →
    burn_river_channel) — see section 5's RIVER-BED BURNING subsection.
  - Output: the unified river_network_depth_estimated.gpkg (+
    river_burned_dem(.tif/_sfincs_grid.tif) — same filenames the "modelled"
    sibling would write). Plots: 10_river_depth.png, 10_river_width_q.png,
    10_river_hydraulics.png (plot_hydraulic_relations_with_estuarine —
    depth-source-coloured markers + correlation subplot; supersedes the
    simpler plot_hydraulic_relations, kept for the disabled-estuarine-model
    code path).

RIVER FORCING steps:
  Step 1:  Identify reaches that cross the domain grid boundary (rule 06's
           output)
  Step 2:  resolve_inside_domain_reaches() — clip the crossing reach's own
           geometry against the domain polygon and use the point where it
           first enters the domain (almost always the same point Step 1
           already found). Only walks to the next downstream reach via
           rch_id_dn when the crossing reach merely touches the domain
           boundary with none of its length actually inside it.
  Step 3:  Filter — enters_domain (at least one rch_id_dn listed reach is in
           the domain network)
  Step 4:  visible_on_grid (inside-domain reach width ≥ SFINCS main-grid
           resolution) is now INFORMATIONAL ONLY — it no longer FILTERS out
           a crossing from Step 5 onward. Previously a narrow crossing at
           fine resolution could strand and silently drop a whole
           downstream branch; has_glofas (which crossings actually get
           forcing) now depends only on enters_domain AND EVA convergence.
           Also: sfincs_res (used for this diagnostic) now uses the MAIN
           grid resolution only — the old subgrid-pixel-count adjustment
           was removed, since subgrid doesn't change what resolution SFINCS
           actually solves hydrodynamics on.
  Step 5:  Snap to GloFAS cell (glofas_search_radius_km: 5.0), filtered by
           glofas_min_mean_discharge. glofas_variable is hardcoded "dis24"
           (the sole variable in this catalogue source) — the old
           glofas_variable config key was removed.
  Step 5b: GRDC correlation diagnostics + optional bias correction (per
           matched GloFAS cell, cached in bias_cache like eva_cache):
           - find_nearest_grdc_station() within
             bias_correction.grdc_search_radius_km (15 km — MOVED here from
             a `river`-top-level key; also used by the always-on correlation
             diagnostic below, not just the opt-in bias correction it now
             lives under) of the crossing's inside-domain point.
           - If found: load_grdc_series() + compute_grdc_correlation() —
             always computes GloFAS/GRDC overlap correlation diagnostics,
             INDEPENDENT of bias_correction.enabled. Requires min_overlap_days
             (730 d / ~2 yr); below that, or if no station within radius,
             returns None (logged).
           - TAIL-FOCUSED CORRELATION: correlation_raw (and, from
             bias_correct_discharge(), correlation_corrected) are restricted
             to overlap days where GRDC discharge is at/above
             bias_correction.tail_percentile (default 90.0) of its own
             overlap distribution — NOT the all-days Pearson r — since this
             pipeline only cares about GloFAS/GRDC agreement at
             flood-relevant high flows. The all-days correlation is still
             computed and returned as correlation_full_raw /
             correlation_full_corrected, for reference/plotting context
             (shown alongside the tail r in plot_bias_correction and
             plot_grdc_overview's scatter panels, with tail days
             highlighted). This is the only place tail_percentile is
             configured (boundary_forcings.river.bias_correction).
           - bias_correct_discharge() wraps compute_grdc_correlation(): only
             if bias_correction.enabled is True (currently FALSE by default)
             AND correlation diagnostics were returned, runs
             empirical_quantile_map() (EQM, n_quantiles=200) with LINEAR TAIL
             EXTRAPOLATION. Otherwise GloFAS series unchanged, diagnostics=None.
           - TODO (in config.yml and the script): the current GRDC extract
             covers only the 8 basins in the 8_polygons.json delta-polygon
             test set (Mississippi, Zambezi, Ebro, Calvert, Mangoky, Vijose,
             Taiwan, Rhine-Meuse) — a global GRDC extract would let this run
             automatically for basins outside that test set instead of
             falling back to GloFAS-as-truth.
  Step 6:  EVA on (bias-corrected or raw) GloFAS discharge → bankfull
           discharge (AMAX/GEV fit, unchanged) + a FULL discharge
           return-period TABLE (POT/GPD fit) — see REDESIGNED EVA OUTPUT
           below; no longer a single flood_discharge scalar.
  Step 6b: [river_processing.empirical_estimation.modify_hydrograph] Compute
           the netted riverine protection-level discharge scalar
           (protection_discharge, from rule 04's protection_levels.json) and
           store it — the actual SUBTRACTION from the timeseries now happens
           at BUILD time (rule 13), not here (see below), since the
           timeseries itself is no longer built in this rule. (There is no
           `protection_levels.enabled` key — see section 4/7's PROTECTION
           LEVELS note on the flopros_range rename and this asymmetric
           coastal-always/riverine-gated netting.)
  Step 7:  Build forcing NetCDF (incl. GRDC provenance vars,
           discharge_rp_table, bankfull_discharge, protection_discharge —
           NOT a pre-built discharge timeseries; see below)

REDESIGNED EVA OUTPUT — return-period table, build-time discharge (NEW):
  Previously, Step 6 fit POT/GPD and immediately extracted ONE scalar
  (flood_discharge at eva.rp_fl), baked directly into a sinusoidal discharge
  timeseries at THIS rule's own run time (build_river_dataset). Changing the
  design return period meant re-running the whole EVA fit.
  Now: gpd_return_value_table() (src/extreme_values.py, vectorized sibling
  of the existing gpd_return_value() — same fit, no re-fitting) evaluates
  the already-fitted POT/GPD curve at a fixed standard set of return
  periods, STANDARD_RETURN_PERIODS_YR = 1, 1.5, 2, then 5-yr steps to 1000,
  then 1000-yr steps to 10000 (212 values), producing discharge_rp_table
  (dims crossing × return_period) — written to river_forcing.nc alongside
  bankfull_discharge and protection_discharge (scalars, as before) and new
  dataset attrs lead_days/period_hr (so rule 13 can reconstruct the wave
  shape without extra config plumbing).
  build_river_dataset() (river_forcing.py) no longer builds a "discharge"
  timeseries variable at all — sinusoidal_wave() is no longer called here.
  The actual design discharge is looked up AT SFINCS BUILD TIME (rule 13)
  via new build_design_discharge_matrix(river_ds, active, design_rp_yr)
  (river_forcing.py): log-RP-interpolates design_q from the table
  (np.interp on log(RP), standard flood-frequency convention, well-behaved
  across the table's 4-orders-of-magnitude RP span), applies the
  protection-discharge floor piecewise (overtopped → bankfull_q + (design_q
  - protection_q); contained-but-above-bankfull → bankfull_q; else
  unchanged) per crossing, then reconstructs the hydrograph via
  sinusoidal_wave(). The ACTIVE SCENARIO's own river_rp drives this lookup
  at build time — design_rp_yr comes from scenario_params(wildcards.
  scenario)["river_rp"] in rule 13 (see section 4/9), not a single
  config.yml value; the removed boundary_setup.design_rp_river_yr and the
  removed boundary_forcings.river.eva.rp_fl config key both predate the
  scenario axis.
  INTENDED CONSEQUENCE: switching scenarios (target_scenarios) or adding a
  new one to scenarios.yml should only require re-running rule 13
  (build_sfincs) onward, NOT rule 07 (get_boundary_forcings/EVA) — a much
  cheaper iteration loop for calibrating the design RP.
  THIS WAS BROKEN 2026-07-28ish -> FIXED 2026-08-02 (see section 14's
  SCENARIO SWITCH RE-TRIGGERED PREPROCESSING entry): for a while,
  07_get_boundary_forcings.py's own rp_fl came from a rule-07 PARAM

REDESIGNED distance formula (previously a single kinematic estimate only):
  final_distance = min(kinematic_distance, attenuation_distance)
    kinematic_distance   = T_eff × (celerity − v_river)
      T_eff    = effective_period_fraction × surge_period_hr × 3600 s
      celerity = sqrt(g × (depth_mouth + surge_amplitude))
      v_river  = Q_bf / (W × D)   [depth_mouth = rivdph]
    attenuation_distance = NEW — marches upstream reach-by-reach (following
      the mainstem, i.e. the largest bankfull_discharge_acc branch at each
      confluence) until friction-damped surge amplitude decays below
      amplitude_threshold_fraction of its own starting value:
        A(x) = A0 · exp(-μx),  μ = r / (2c),
        r = (8/3π) · g · n² · U0 / h^(4/3)
      channel Manning's n = testing.upstream_boundary_check.channel_manning_n.
      U0 (reference velocity) is computed ONCE at the mouth and held FIXED
      for the whole march — re-deriving U0 from the locally-decaying
      amplitude at each step would make the decay non-convergent
      (hyperbolic, not exponential).
  depth_mouth and v_river are used exactly as calculated -- no config floor
  (the old min_depth_at_mouth_m / min_river_velocity_ms were removed
  earlier; amplitude_threshold_fraction is the newest replacement/addition
  for the attenuation branch specifically). A mouth with no usable
  calculated depth/velocity is skipped entirely (logged), not substituted.
  Each mouth now uses its OWN NEAREST CoastRP station's rp_level as surge
  amplitude (not the domain-wide max — stations can vary 5-10x across one
  basin).
  Forcing points must be OUTSIDE the (now-tighter-of-two) distance from
  river mouths. Blocked mouths (v ≥ celerity, kinematic branch
  undetermined): drawn as orange X markers.
  Config params (testing.upstream_boundary_check): effective_period_fraction
  (0.5), channel_manning_n (NEW), amplitude_threshold_fraction (NEW).
  Plot title reports the tightest margin (distance-from-mouth minus the
  final min() distance) found across all forcing-point/mouth pairs; subtitle
  "min depth"/"min v" are the smallest CALCULATED values found. Plot gains a
  LineCollection overlay coloring reaches by remaining amplitude along the
  attenuation march (new), on top of the existing geodesic-circle +
  river-network base:
        Green dot = forcing point outside the critical radius (safe)
        Red dot   = forcing point inside the critical radius (too close)

IMPORT VERIFICATION NOTE: `ast.parse` and `snakemake -n` only catch syntax
errors and DAG-shape problems — neither catches a broken `from src.X import
Y` statement, since that is syntactically valid and only fails at actual
script-execution time (ModuleNotFoundError / AttributeError). After renaming
or deleting a src/ module, or moving a function between modules, verify with
an actual import-resolution check: parse every workflow/scripts +
workflow/src + tests file's `from src.X import Y` statements, import each
module X (with workflow/ on sys.path), and confirm Y is a real attribute. A
plain grep for the old module/function name is necessary but not sufficient
when the rename touches many call sites — it's easy to miss one.

IDE FALSE POSITIVES:
  Snakefile: VS Code flags BASINS as undefined and expand() as unused.
  These are ALWAYS false positives — BASINS is defined in 00_common.smk via
  Snakemake include:, which the Python linter doesn't understand. The
  "snakemake is not defined" warning in every workflow/scripts/*.py file is
  the same kind of false positive — the `snakemake` object is injected by
  the Snakemake `script:` directive at runtime, not imported.
  GeoSeries.x / .y attribute errors in IDE are also false positives (pyright
  doesn't know the GeoSeries type).

RASTER ALIGNMENT:
  calculate_default_transform adds padding → extent > wgs84_bounds → visual
  misalignment. Fix: pass dst_bounds to _to_wgs84_grid() to use from_bounds.

HARD-MERGE FILLNODATA COST (fixed, basin 4267691 investigation):
  05a_get_elevation.py's step-4 hard merge (FathomDEM valid ⇒ FathomDEM,
  else GEBCO) ends with a "defensive fallback" fillnodata() call for pixels
  where NEITHER source had data — meant to be rare, per its own comment.
  But `_remaining = np.isnan(merged)` is computed BEFORE the `outside_domain`
  mask is applied, and topo_utm/gebco_utm are already NaN everywhere outside
  domain_poly (each was clipped to the polygon before reprojection) — so for
  any basin whose delta polygon doesn't fill its own rectangular bounding
  box (the common case), `_remaining` includes the ENTIRE outside-of-polygon
  area, not just genuine gaps. The call used `max_search_distance =
  max(merged.shape)` (essentially "search the whole raster"), so GDAL's
  IDW fill was asked to search up to ~15,000 px deep for millions of
  pixels — and the very next line (`merged[outside_domain] = np.nan`)
  immediately discards every one of those results. On basin 4267691
  (15,276×10,294 px working grid) this took ~3 HOURS by itself (confirmed
  via file mtimes: no output between 05a_elevation_mdt_ocean.png and
  05a_elevation_datum_correction.png), while everything else in the
  pipeline moved at normal speed. Swapping the order of the two masking
  lines does NOT fix this — outside_domain pixels are already NaN in
  `merged` either way, so `_remaining` is identical regardless of order.
  Fix: bounded `max_search_distance` (100 px, a named constant
  `_GAP_FILL_MAX_SEARCH_PX`) instead of the full raster dimension — genuine
  small interior gaps (the actual intended case) still get filled correctly
  from real nearby data within that radius; the huge outside-domain region
  now gets a cheap, fast "nothing valid nearby" per pixel instead of an
  unbounded search. Deliberately NOT fixed by assigning outside-domain
  pixels a numeric sentinel (e.g. -999.999) instead of NaN: fillnodata's
  IDW would then treat those sentinel pixels as valid SOURCE data and could
  blend a wildly wrong numeric value into a genuine nearby interior gap's
  fill — a silent correctness bug, worse than the original performance
  bug. NaN reliably propagates/fails loud; a numeric placeholder doesn't.
  If a similar unexplained multi-hour stall ever recurs in this script (or
  a similar hard-merge/fillnodata pattern elsewhere), check for an
  unbounded max_search_distance BEFORE assuming a data-size or environment
  problem — file mtimes of the diagnostic plots either side of the
  suspected slow section are how this was actually pinpointed, since
  fillnodata/reproject calls here aren't wrapped by ScriptProfiler.

MDT EXTRAPOLATION:
  MDT is NaN over land. Must call rasterio.fill.fillnodata() on the raw WGS84
  clip BEFORE resampling to UTM grid (applies to GEBCO's MDT correction in
  rule 05a; the DEM itself is never MDT-corrected, only geoid-offset
  corrected). Load with 5° margin (mdt_load_margin_deg) to ensure sufficient
  offshore reference pixels.

QUADTREE POSTPROCESSING MEMORY (fixed, three rounds -- basin 4267691, run_spinup):
  get_bed_level()'s subgrid reference raster (used to rasterize a quadtree
  mesh field onto a regular grid) can be large enough on its own, for a big
  domain, to blow past available memory -- not because the domain is
  unusually finely refined everywhere, but because the OLD mosaic logic
  applied the FINEST quadtree level's native pixel size across the WHOLE
  domain extent, even where only a small fraction of cells are actually
  refined that finely. Three rounds, each one layer deeper than the last:
  Round 1: compute_max_inundation -> hydromt_sfincs.utils.downscale_floodmap
    -> zsmax.ugrid.rasterize_like(dep) tried to allocate a (25180, 37500)
    float64 array (7+ GiB) and raised numpy ArrayMemoryError.
    Fix: src.postprocessing._coarsen_for_memory() (renamed from
    _coarsen_for_timeseries, which used to run only for animation time
    series under the wrong assumption a single frame always fits) now also
    runs inside compute_max_inundation with n_frames=1 whenever zsmax is a
    UgridDataArray (quadtree) -- coarsens the reference raster BEFORE it's
    used as the rasterize_like target, whenever the native resolution
    exceeds max_bytes (default 500 MB).
  Round 2: _coarsen_for_memory()'s OWN da_ref.coarsen(...).mean() call then
    failed too: "Unable to allocate 900. MiB for an array with shape (8393,
    3, 12500, 3) and data type bool". Cause: da_ref arrives already fully
    materialized (eager numpy-backed -- get_bed_level's rioxarray/
    data_catalog reads are not chunked); an un-chunked .coarsen().mean()
    with the default skipna=True needs to build nanmean's internal isnan
    mask (and other reduction bookkeeping) at a size comparable to da_ref
    itself, ON TOP of da_ref already resident -- enough on its own to
    exceed available memory even at "only" 900 MiB, since so little
    headroom remained after the ~7.5 GiB source array. Fix: da_ref.chunk({
    "y": 2000, "x": 2000}) before .coarsen(...).mean(), then .compute() only
    the final (already-small, coarsened) result.
  Round 3: even BEFORE either of the above ran, get_bed_level() ->
    _mosaic_quadtree_dep_levels() itself failed while BUILDING the mosaic:
    mosaic.where(~mosaic.isnull(), da.rio.reproject_match(mosaic)) tried to
    allocate a (25180, 37500) float32 array (3.5 GiB). Cause: the old
    implementation opened each dep_subgrid_lev*.tif at NATIVE resolution
    (rioxarray.open_rasterio without chunks reads eagerly) and reprojected
    every coarser level onto the FINEST level's native full-domain grid
    before combining -- so the huge array existed before either Round 1 or
    Round 2's fixes ever got a chance to run. Fix (the actual root-cause
    fix; Rounds 1-2 remain as defense-in-depth but are now mostly no-ops for
    the single-frame case): rewrote _mosaic_quadtree_dep_levels() to read
    each level directly at a shared, memory-bounded target resolution via
    plain rasterio (`ds.read(out_shape=..., resampling=Resampling.average)`
    -- a decimated read that never materializes the native-resolution array,
    unlike rioxarray's default eager open), computed from the same
    max_bytes-driven factor formula as _coarsen_for_memory. Levels are still
    combined finest-first (np.where(isnan(mosaic), coarser, mosaic)), so
    refined-zone detail still wins where present -- just built at a bounded
    resolution from the start instead of coarsening an already-huge array
    after the fact.
  If a similar ArrayMemoryError ever recurs in a NEW postprocessing/plotting
  function that touches get_bed_level()'s reference raster or the quadtree
  per-level dep files directly, check whether it's reading/building at
  NATIVE resolution somewhere upstream of any coarsening (Round 3's mistake)
  before assuming the existing _coarsen_for_memory() safety net will catch
  it -- that net only helps once the array is already in memory.
  Round 4 (fixed, basin 4267691, modelled_depth_estimation/rule 10): despite
  the name, this risk was never actually quadtree-specific -- Round 1's own
  fix gated _coarsen_for_memory() behind `isinstance(da_zsmax, xu.
  UgridDataArray)` in BOTH compute_max_inundation and compute_flood_
  timeseries_stats, so a REGULAR grid (rule 10-modelled always builds one,
  it has its own NotImplementedError guard against quadtree) got no memory
  bounding at all -- basin 4267691's own regular-grid subgrid reference
  raster (~700M pixels / ~2.8 GB uncompressed) crashed round 0's own
  diagnostics with no traceback. Fixed by dropping the quadtree-only gate
  in both functions -- _coarsen_for_memory() already no-ops below its own
  max_bytes threshold, so calling it unconditionally is safe for both grid
  types.

DISCHARGE POINTS NOT SNAPPED TO THE NETWORK CENTERLINE (fixed, basin
4267691 investigation):
  Neither hydromt_sfincs's own discharge_points.create() nor this
  codebase's existing point-wrangling (geometry.snap_points_into_region,
  which only nudges a point back inside the model's active region) ever
  checked that a discharge point's resolved SFINCS grid cell actually sits
  on the modelled channel. A crossing's domain-entry point is geometrically
  exact, but nothing guaranteed the grid cell it rasterizes onto was part
  of channel_mask -- on a coarse enough grid it could land on a
  neighbouring floodplain cell with no real conveyance instead. Very likely
  what produced basin 4267691's round-0 calibration water-level spike
  (369 m at one location): a large constant discharge injected into a cell
  with no channel depth to carry it.
  Fixed via new river_burn.snap_points_to_centerline_cells() -- see section
  11's river_burn.py entry for the full mechanism. Wired into BOTH
  10_depth_estimation_modelled.py and 13_build_sfincs.py's regular-grid
  discharge forcing. Regular grid only -- no quadtree equivalent of
  build_centerline_cells_regular exists yet.

SEED REACH ROUNDED-CAP (fixed, raised independently during the same
investigation):
  Every per-reach channel buffer in river_burn.py (channel_mask, the burn
  excavation corridor, the weir-smoothing corridor) is built via a plain
  line.buffer(width/2.0), which defaults to a ROUND end cap at both ends.
  Harmless at an internal junction (a neighbouring reach's own buffer
  already overlaps and covers the join regardless of angle), but wrong at
  a network SEED reach (is_seed=True, no upstream neighbour): the round
  cap bulges out in an arc beyond the line's own true start vertex,
  enclosing extra channel cells build_centerline_cells_regular never
  samples (it only follows the raw line, not the buffer) -- invisible to
  per-cell calibration tracking, yet inside the same confined pocket as
  the actual discharge-injection cell.
  Fixed via new river_burn._flush_capped_buffer()/_half_plane_beyond() --
  see section 11's river_burn.py entry. Wired into all FOUR existing
  line.buffer(...) call sites with clip_start=bool(row.is_seed); every
  other reach keeps its plain round-capped buffer unchanged. Terminal/
  mouth reaches (no downstream neighbour) have the same bulge but are
  scoped out for now -- their downstream end transitions into the coastal
  weir/ocean_mask handling through a different mechanism, not confirmed
  safe to flush-cap yet (clip_end stays False everywhere).

WEIR TOPOLOGY GAPS (fixed, found by directly inspecting basin 2433835's
own coastal_protection_weir.gpkg):
  REQUIREMENT: every weir segment's endpoint must either connect to
  another segment, or lie on the delta polygon's own boundary -- the whole
  weir must resolve into continuous boundary-to-boundary chains or fully
  closed loops, NEVER a dangling gap in the middle (a break lets water
  flow straight through at exactly that point). Endpoint-connectivity
  analysis on the actual file found 38 dangling endpoints out of 3547
  segments, none of them legitimately at the domain boundary -- real,
  confirmed breaks.
  Root cause: protection_weir.py's edge-tracing functions
  (_seaward_edges_regular_with_values / _seaward_edges_quadtree_with_values,
  shared by both grid types via seaward_edges_with_values) detect a
  land/water_like transition purely geometrically, but silently DROP the
  segment if that cell's crest_surface value is NaN. crest_surface =
  max(elsewhere_crest, river_crest_on_grid); river_crest_on_grid
  legitimately has NaN gaps beyond its own dilation radius, but
  elsewhere_crest (coastal_crest_on_grid, rule modelled_depth_estimation's
  own per-cell probe-derived array) can ALSO have NaN holes beyond its own
  probe/dilation coverage (e.g. a land cell next to a small isolated water
  patch that's neither a modelled river reach nor near a coastal probe).
  Wherever both are NaN at once, the segment vanished.
  Fixed in build_coastal_protection_weir(): elsewhere_crest now falls back
  to the flat crest_elevation_m scalar wherever coastal_crest_on_grid
  itself is NaN -- exactly what "no per-cell override available" already
  means everywhere else that array doesn't cover. crest_surface is now
  guaranteed finite at every land cell, so the edge tracer's NaN-drop
  branch never actually triggers for this call path (seaward_edges_with_
  values has exactly one caller, build_coastal_protection_weir, so fixing
  the input at the source was safe and sufficient -- the tracer's own
  drop-on-NaN branch was left in place as a defensive no-op, not removed).
  Verified with a synthetic unit test (straight 10-cell coastline, a
  deliberate NaN hole at one cell) -- produces exactly 10 segments, none
  dropped, the NaN cell correctly falling back to the flat scalar crest.

WEIR TOPOLOGY GAPS (DIAGONAL 4-CONNECTIVITY) (fixed, found tracing basin
2433835's weir geometry directly -- no SFINCS run needed, weir line
positioning depends only on grid/channel_mask/land classification):
  A SECOND, distinct cause of dangling weir endpoints, found even after
  the NaN-drop fix above was already in place: GridArrays.
  connected_components() (discard_small_components' only caller, used to
  drop land/water patches smaller than min_component_cells) used scipy.
  ndimage.label()'s DEFAULT 4-connectivity (only edge-sharing neighbours
  count as connected). A real, physically continuous coastline commonly
  narrows to a single DIAGONAL-only pixel-to-pixel connection at some
  point (an ordinary raster-discretization artifact for a jagged
  coastline, not a genuine break in the landform) -- under 4-connectivity
  that diagonal touch does NOT count as connected, so a large mainland and
  a small diagonally-attached tail get classified as two SEPARATE
  components, and the small tail (confirmed on basin 2433835: ~7 cells,
  well under min_component_cells=30) gets dropped as if it were a real,
  isolated small island. The dropped cells become neither land_mask nor
  water_like, and the edge tracer draws no segment against either side of
  them (same "neither" mechanism as the NaN-drop bug above, different
  root cause) -- the boundary stops dead at the pinch point instead of
  continuing along what is, physically, the same landform.
  Fixed by switching connected_components()'s regular-grid branch to
  8-connectivity (self._struct8 = generate_binary_structure(2, 2),
  treating a diagonal touch as connected) -- the ONLY caller is
  discard_small_components, so this doesn't affect close_gaps (which
  intentionally keeps its own separate 4-connectivity self._struct4, since
  that one represents actual grid-step distance for dilation, not a
  landform-continuity question) or the quadtree branch (mesh face_face_
  connectivity is a real physical adjacency graph already, no diagonal
  ambiguity applies).
  Verified with a synthetic unit test (25-cell block + 4-cell tail joined
  only diagonally -- previously the tail was dropped, now both are kept as
  one 29-cell component) and by re-tracing basin 2433835's actual weir (4
  dangling endpoints -> 2; the remaining 2 are a distinct, minor, unfixed
  issue in far corners of the rectangular grid bounding box with no land
  or channel nearby at all -- not this bug, not yet investigated further).

MOUTH CREST NEVER VERIFIED AGAINST THE REAL WATER LEVEL (fixed):
  10_depth_estimation_modelled.py's own zs+freeboard_m<=crest condition
  holds well along the centerline, but the mouth reach's own last cell was
  a special case that bypassed it entirely: every round (round 0, every
  correction round, even the final exact-tightening snap) unconditionally
  set weir_crest_current[is_last_mouth_cell] = dem_at_cell[is_last_mouth_
  cell] -- the raw seabed elevation, only ever floored afterward by the
  flat coastal_protection_crest_m scalar, never checked against that
  round's own actual simulated water level at all (unlike every other
  centerline cell AND the coastal/river-boundary probe cells).
  Fixed: mouth crest is now max(period-max water level at the nearest
  OCEAN-classified cell + freeboard_m, coastal_protection_crest_m)
  (_mouth_crest_target, new small "mouth ocean probe" -- one nearest-
  ocean-cell per mouth reach, same _resolve_map_cell_idx/_read_map_zs_
  at_cells machinery every other probe uses). Deliberately samples the
  OCEAN side, not the mouth's own river-side channel cell -- that cell
  sits right at the coast/river transition and isn't necessarily
  representative of the open water the crest actually holds back
  (mirrors the river-boundary probe's own "look across the dike" logic).
  Bed/depth at the mouth is UNCHANGED (still hard-forced to natural
  bathymetry, a real physical constraint) -- only the crest formula
  changed, at all three places it used to be hard-forced to dem_at_cell.
  Known residual, not addressed: if backwater consistently raises the
  RIVER side above the ocean side at the mouth, this fix alone won't
  catch it (only the ocean side is sampled) -- flagged, not yet decided
  whether to also take the max against the river-side centerline cell's
  own reading there.

DISCHARGE-BUFFER PROBES SAMPLED ONLY THE INJECTION CELL'S OWN NEAREST
CHANNEL CELL, NOT THE LOCAL PEAK (fixed):
  Near a seed/head reach, the discharge injection cell's own water level
  is not necessarily the local peak -- a narrow/bottlenecked head can push
  the true peak a cell or two away (see this module's own long-standing
  "sharp local spike" caveat about the injection cell itself). The river-
  boundary probe mechanism sampled EVERY probe cell, including ones inside
  a discharge point's own 5-cell buffer, at a single nearest-channel-cell
  reading, which could miss that off-injection-cell peak.
  Fixed: river_boundary_probe cells inside a discharge point's own buffer
  zone (_discharge_buffer_land) now sample the MAX water level across
  every channel cell within that SAME radius of their nearest discharge
  point, instead of one nearest-cell reading (falls back to the nearest-
  cell reading if that local neighbourhood is somehow empty). Ordinary
  dike-adjacent probes elsewhere are unaffected. Since the weir build
  already combines the centerline's own per-cell crest and this probe
  correction via np.maximum, the centerline's own more-precise,
  round-verified value still wins wherever it's higher -- this only ever
  raises protection further where the centerline is silent or lower.
  Verified with a synthetic test of the new index/aggregation logic.

WEIR TOPOLOGY GAPS (DISCARDED SMALL FEATURES LEFT AS HOLES) (fixed, found
tracing basin 4267691's weir geometry standalone -- a much bigger, more
complex coastline than 2433835):
  A THIRD distinct weir-topology-gap mechanism, on top of the NaN-drop fix
  and the diagonal-4-connectivity fix above: discard_small_components()
  (called separately on land_mask and water_like, to drop small islands/
  patches below min_component_cells) leaves every discarded cell as
  neither land_mask nor water_like -- invisible to the edge tracer
  (h_break/v_break require one side True and the other True; a cell
  reading False on both gets no segment drawn against it from either
  direction). Where a discarded small feature sits at the true edge of a
  larger, still-kept feature, this doesn't just skip a ring around the
  excluded feature itself (the intended behaviour) -- it also breaks the
  LARGER feature's own boundary trace at that exact point, leaving a
  dangling gap in what should still be a continuous coastline.
  Fixed in build_coastal_protection_weir(): a cell discarded from
  land_mask is now reclassified into water_like instead of being left as
  a hole, and vice versa for a discarded water_like cell reclassified
  into land_mask -- a too-small island dissolves into its surrounding
  water, a too-small pond dissolves into its surrounding land, either way
  producing a genuine continuous transition at the larger feature's own
  true edge (or no segment at all, where the discarded feature was fully
  isolated) -- achieving the original "no ring around a small excluded
  feature" intent without leaving an untraceable gap behind.
  land_mask_raw/water_like_raw are mutually exclusive by construction
  (land_mask_raw = ~water_like_raw & valid_mask), so the two reclassified
  sets can never collide with each other or with the surviving mask on
  the opposite side -- proven via a synthetic exclusivity/coverage test.
  Verified empirically on both basins: 2433835 unaffected (4010 segments
  vs. 3988 before, same 2 pre-existing array-edge dangling points, no
  regression). 4267691: 22 -> 16 dangling endpoints -- all 6 resolved
  were genuine coastline small-feature cases; the remaining 16 are now
  EXCLUSIVELY the array-bounding-box-edge case (see next entry).

MESH-NATIVE ANIMATION (flood progression):
  hydromt_sfincs itself never rasterizes a quadtree mesh for PLOTTING —
  SfincsModel.plot_basemap() and xugrid's own da.ugrid.plot() render mesh
  data directly as a matplotlib PolyCollection built from the mesh's own
  cell polygons (memory scales with cell COUNT, not a rasterized pixel
  grid). The only rasterize_like() call anywhere in hydromt_sfincs is
  downscale_floodmap's genuine subgrid-resolution downscaling (a real
  analysis product, not a plotting convenience) — exactly the operation the
  quadtree-memory fixes above had to make memory-safe. Our own animate_
  flood_progression used to rasterize EVERY quadtree field before plotting,
  even though animations don't need subgrid-level pixel detail at all —
  purely a plotting convenience, unlike compute_max_inundation's actual
  downscaled analysis output.
  compute_flood_progression() (src/postprocessing.py) now returns h = clip
  (zs - zb, 0) mesh-native (xu.UgridDataArray, CRS restored via
  _ensure_ugrid_crs/mod.crs if missing) for a quadtree run, WITHOUT
  rasterizing and WITHOUT land/water masking (the land polygon overlay
  already shows the water boundary visually; sampling land-use per mesh
  cell centroid would be extra complexity for a purely cosmetic effect).
  plots.animate_flood_progression detects xu.UgridDataArray and renders via
  _mesh_overlay_setup() (reprojects land/river/domain overlays onto the
  MESH's own native CRS, e.g. UTM — not WGS84 like every raster-based plot
  in this module, since xugrid has no simple .rio.reproject() equivalent for
  a mesh's topology) + da.isel(time=0).ugrid.plot() building a PolyCollection
  once, updated per frame via collection.set_array(values.ravel()) — never
  rasterizes. Regular-grid runs are completely unaffected (same imshow path
  as before).
  VELOCITY ANIMATION WAS REMOVED ENTIRELY (out of scope for this project) —
  plots.animate_velocity, postprocessing.compute_velocity_timeseries,
  sfincs.sanity_checks.velocity_animation.enabled, the animation_velocity
  rule outputs, and storevel wiring in rules 13/14 are all gone. storevel is
  now hardcoded to 0 in both rule 13's and rule 14's sfincs.inp — nothing
  ever needs instantaneous u/v output anymore. Before removal, a candidate
  mesh-native rendering for velocity was investigated and rejected: SFINCS
  stores u/v on a SEPARATE staggered "interface/flux point" topology
  (SFINCS's own regular-grid output reader splits face vars like zs/zb from
  edge vars like u/v/qx/qy; the quadtree kernel's internal "uv point"
  bookkeeping is architecturally distinct from and not equal in count to the
  face/z-point set) — so u/v could not have been safely assumed to carry a
  usable Ugrid2d FACE mesh for direct mesh-native plotting the way zs/zb
  reliably do. Worth knowing if velocity output is ever needed again.
  Area/volume STATISTICS (flood_timeseries.csv, the sanity-check inundation
  ratio) deliberately did NOT move to mesh-native math, despite this being
  the obvious-looking next step: compute_max_inundation's da_hmax is already
  a UNIFORM-resolution raster (downscale_floodmap's output grid), so pixel-
  counting has no variable-cell-size bias to fix, and switching to summing
  raw per-cell mesh areas would mean losing the subgrid within-cell bed
  detail SFINCS subgrid modeling exists to capture (each quadtree cell would
  fall back to its own single zb value) -- a real accuracy downgrade for
  cells with significant internal bed variation (riverbanks, levees), not a
  neutral reformulation. Instead: compute_flood_timeseries_stats() (NEW
  function, src/postprocessing.py) decouples the CSV's per-timestep area/
  volume from compute_flood_progression()'s now-mesh-native animation output
  entirely -- processes ONE timestep at a time via hydromt_sfincs.utils.
  downscale_floodmap (same function/resolution compute_max_inundation uses)
  onto the SAME (already memory-bounded) reference grid, computes that
  frame's stats, discards it, moves on. This decouples memory cost from
  frame count entirely (previously, the whole multi-frame series had to be
  rasterized onto the reference grid at once, forcing a coarser max_bytes
  budget to fit ALL frames simultaneously) — so stats now use
  STATS_MAX_BYTES (1.5 GB, single-frame) instead of animation's shared
  500 MB default, meaning genuinely MORE accurate stats than before, not
  just a memory fix. downscale_floodmap is called with hmin=0.0 (not
  threshold_m) so flood_volume_m3 sums ALL positive depth present in the
  domain, matching a literal "total flood volume" -- threshold_m is applied
  separately, only to decide which pixels count towards flooded_area_km2.
  Round 4 (basin 4267691, run_event): compute_flood_timeseries_stats's own
  get_bed_level -> _mosaic_quadtree_dep_levels crashed AGAIN, now inside
  mosaic.rio.write_crs(...).rio.write_transform(...) — "Unable to allocate
  1.76 GiB" for an array already sized right at STATS_MAX_BYTES. Cause:
  rioxarray's write_crs()/write_transform() deep-copy the WHOLE array by
  default (inplace=False) even though they only touch metadata — chaining
  two out-of-place calls on an array already at the memory budget needs
  multiple simultaneous full-size copies. Fix: pass inplace=True to both
  (in _mosaic_quadtree_dep_levels AND _coarsen_for_memory's own write_crs
  call) — sets metadata directly, no copy. If a similar crash ever recurs
  right at a `.rio.write_*()` call specifically (not the surrounding
  compute), check for a missing inplace=True first.
  _rasterize_like() and _n_frames() (formerly used by compute_velocity_
  timeseries and the old rasterizing compute_flood_progression) were
  removed as dead code once nothing called them anymore — the ONLY
  remaining raster-projection path in postprocessing.py is
  hydromt_sfincs.utils.downscale_floodmap (compute_max_inundation,
  compute_flood_timeseries_stats), which correctly downscales BOTH grid
  types (unlike _rasterize_like, which was a no-op for a regular grid and

  _coarsen_for_memory()'s n_frames parameter was also dropped (simplified
  to always assume a single frame) once every remaining caller passed 1 —
  velocity's multi-frame usage was the only caller that ever passed
  anything else.

  (preprocess/build/all) directly, no per-file target list needed:
    snakemake build --cores N --config target_basins="[2433835]" --forceall
  --forceall forces every job for that basin to re-execute even if its
  outputs look up to date; drop it to only rerun what's missing/stale.
  Unknown basin_ids raise a ValueError at config-parse time (before the DAG
  is built) rather than silently producing an empty/wrong DAG.

SNAKEMAKE OUTPUT SYNC:
  Always keep _PREPROCESS_OUTPUTS / _BUILD_OUTPUTS in Snakefile in sync with
  rule outputs, including the config-conditional blocks (river conditioning,
  subgrid, quadtree, spinup). MissingInputException for tracked outputs
  almost always means one of these lists is stale. Validate with
  `snakemake -n` after any rule/output change.

SNAKEMAKE FAILURE CLEANUP:
  Snakemake's failure-cleanup deletes ALL declared outputs of a failed job,
  including any raw simulation output already written before the failure
  (e.g. sfincs_map.nc, the .rst restart file from rule 14) even if the
  underlying SFINCS run itself completed successfully. There is no way to
  recover a crashed job's outputs without re-running the failed rule; only
  upstream rules whose own outputs are already on disk and untouched can be
  skipped.

SFINCS MODEL BUILD:
  HydroMT-SFINCS 2.0.0.dev0: use component-based API.
  Open SfincsModel in 'w+' mode for full build — NOT 'r+' (causes sfincs.ind errors).

RIVER ID HANDLING:
  reach_id from SWORD may be int or string; always normalise with
  str(int(float(x))) pattern before any dict/set operations.

BIFURCATION DISCHARGE (SIMPLIFIED):
  Weight = width only — PURE width-proportional split, applied inside rule
  08's own accumulate_discharge() call (see section 6 — this is no longer a
  separate rule "09a"). The previous angle-weighted scheme (weight = width
  × angle_factor) was REMOVED entirely; it had never been
  sensitivity-tested, and rule test_bifurcation_calibration_options (rule
  11, section 8) now treats this simpler width-proportional split as the
  production baseline being compared against alternate SWORD sources (the
  standalone tests/test_bifurcation_calibration_options.py script that used
  to mirror this comparison outside Snakemake has since been removed — see
  section 13; the rule itself is still current). Only applies at
  len(dn) > 1 (single-arm transitions: full discharge passes through
  regardless).

MONOTONE ELEVATION (rule 09 is now the ONLY mechanism, and ALWAYS runs):
  rule 09 (condition_elevation, rule name enforce_river_monotonicity, no
  longer opt-in): enforce_river_monotonicity() modifies the DEM RASTER

  elevation_conditioned.tif (+ its SFINCS-grid-resolution copy — see
  section 5). Cycles are detected with a warning; DAG assumption required

  07_forcing_timeseries.png's protection-discharge lines -- NEITHER was a
  bug in the actual RP->discharge computation (bankfull_discharge/
  flood_discharge/protection_discharge are correctly monotonic in RP;

  reproducing with real pyextremes calls). Fixed by explicitly restoring
  tick label visibility + labelbottom on both top-row axes after all

  for basin 4267691 this picked a minor crossing (flood_discharge ~5,500

  bias_cache, same (i_lat, i_lon) keys) so the diagnostic always re-fits on

ZSINI BASELINE CONNECTIVITY FIX (fixed — was silently broken on most basins):
  13_build_sfincs.py shifts zsini's sea cells (0.0 in zsini.tif, rule 05b)
  to baseline_m (the mean MDT+SLR vertical correction read from
  surge_forcing.nc) so the model's initial ocean level matches the boundary
  forcing's own vertical reference. A "connectivity fix" then reverts any
  sea cell NOT reachable from "the open ocean" back to its own bed
  elevation (dry start) — meant to stop isolated low-lying ponds/
  depressions from starting artificially wet.
  THE BUG: "reachable from the open ocean" used to mean "belongs to a
  connected-component of sea cells that touches the raster ARRAY's own
  rectangular edge" (row 0/-1, col 0/-1). This silently assumes the domain
  polygon's own footprint reaches all the way to its bounding-box raster's
  edges — false for essentially every basin here (the delta-polygon +
  domain.delta_buffer_m clip sits well inside a much larger rectangular
  UTM grid, NaN-padded in the corners — see any 05a_elevation.png). So the
  array's actual edge pixels are almost always outside-domain nodata, not
  real sea, and the "edge-touching" component set came out EMPTY (or only
  accidentally non-empty) for most basins — meaning the fix treated nearly
  the ENTIRE real open ocean as "isolated" and reverted it to bare bed
  elevation instead of baseline_m. Confirmed via existing build logs before
  the fix: basin 2433835 (baseline_m=-0.3955) had 315,243 of ~587k real
  sea cells wrongly reverted; 4267691 had 235,792; 1248635 had 76,674;
  2444235 had 42,997; 2209166 had 512. Only 2 of 8 already-built basins
  (1475442, 620947) happened to have a domain shape where the array edge
  genuinely coincided with real sea, masking the bug there. Symptom in
  06_zsini.png (rule 13's own diagnostic plot, visuals/sfincs_build/): the
  uniform baseline_m color only appeared right at the coast (where real
  bed elevation happens to be close to baseline_m anyway) while open water
  further offshore showed each cell's own bed elevation instead of a flat
  plane — looks exactly like "zsini isn't being set at sea", though the
  underlying baseline_m computation itself was always correct.
  THE FIX: replaced "touches the array edge" with "is the SINGLE LARGEST
  connected sea component" (np.bincount over the scipy.ndimage.label output,
  excluding background) — geometry-independent, no assumption about where
  the domain sits within its own bounding-box raster. Verified: basin
  2433835 now correctly shows uniform -0.3955 m across the entire real
  ocean, with only 7 genuinely isolated cells (small ponds, landuse classes
  30/90 — vegetation/wetland, nowhere near open water) reverted to dry.
  CONSIDERED AND REJECTED: using landuse.tif's landuse==200 ("Sea", see
  src.plots._LC_NAMES) directly instead of this connectivity approach —
  checked empirically for basin 2433835 and it's worse on both ends:
  landuse.tif is reprojected onto the FULL bounding-box grid, not clipped
  to the domain polygon, so landuse==200 matches 839,298 px but only
  328,812 of those are actually inside the real domain (the rest is
  outside-domain territory the pipeline never used to consider "sea" at
  all); and even restricted to the real domain, landuse==200 MISSES 12,898
  (3.9%) of the cells OSM/the current fix correctly call "connected open
  sea" — mostly ones Copernicus's 100 m classifier assigns to landuse=80
  ("inland water") instead of 200, likely in exactly the complex lagoon/
  estuary/river-mouth cells common in a delta, where OSM's coastline
  vector data is more reliable than a coarse global land-cover product.
  Switching to landuse==200 would have reintroduced a smaller version of
  the same class of bug just fixed.

  manual `pre-commit run` and an actual `git commit`, check
